# Round 1：用户旅程图

本轮只完成一个目标：基于截图中的真实操作记录，梳理出目标产品从输入需求到最终产出的"用户旅程图"。

## 一、取证要求

从最早一张截图开始，按时间顺序完整查看：
1. 用户最初提交了什么：原始需求、配置参数、风格、参考素材
2. 产品第一次如何回应
3. 产品让用户确认了哪些信息；每次确认后，页面新增或修改了什么
4. 用户在哪些地方可以：满意并继续 / 提出修改 / 选择不同方案 / 中断任务 / 返回前一步
5. 产品如何处理：正常生成、用户纠偏、生成失败、额度不足、用户中断
6. 聊天记录、任务状态和画布/资产是否存在不一致

不要只看对话文字，还要同时检查：页面按钮、表单选项、资产卡片、资产历史记录、当前任务状态、预览和导出/剪辑入口、错误提示及后续操作。

## 二、证据规则

所有结论分三类：
- 【页面事实】：页面中可以直接看到
- 【合理推断】：由多条页面事实推导得出
- 【尚未确认】：当前页面证据不足

特别注意：
- Agent 说"已完成"不代表实际完成，必须检查画布或资产状态
- Agent 说"符合要求"不代表结果真的符合，必须查看最终输出
- 聊天状态和画布状态冲突时明确记录，不能自行选择一个当成事实
- **不要还原 Agent 调用流程，不要编写 System Prompt——本轮只关注用户经历了什么**

## 三、先输出用户旅程证据表

按以下结构整理：

| 阶段 | 用户目标 | 用户动作 | 页面反馈 | 用户需要做的决定 | 页面/资产状态变化 | 问题或阻力 | 证据 |

"证据"栏必须写清楚对应的：页面原文、按钮名称、Agent 名称、可见资产、错误信息、**截图编号**。

## 四、再生成用户旅程图（HTML）

只保留三条泳道：用户 / 产品界面 / 系统结果。

每个节点表达清楚：用户想完成什么、执行了什么动作、页面给了什么反馈、是否需要做选择、选择后进入什么状态、失败后怎么处理。

必须包含三类路径：正常主流程、用户修改/纠偏流程、失败与中断流程。
每个判断节点用菱形，每条分支写明条件（如：满意/不满意、生成成功/失败、继续/中断、余额充足/不足）。

图中每个节点标注对应的证据编号（截图编号）。

## 五、交付顺序

1. 本次查看范围
2. 无法访问或无法确认的证据
3. 用户旅程证据表
4. HTML 格式用户旅程图，包含：完善的用户操作流程、**用户情绪**、**遇到的痛点**（支持用户补充）、**用户的想法与感受**、**同类产品机会点**（如果我要做同类产品，有哪些产品机会点）
5. 图中每个节点对应的证据编号
6. 三个最值得讨论的用户体验问题

**完成后停下，等待用户确认。不要继续拆 Agent 调用流程、System Prompt、工具列表或全局上下文。**（这是整个拆解流程中唯一的停顿点）
