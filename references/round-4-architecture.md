# Round 4：产品全景架构图

基于 Round 1–3 的已有材料（用户旅程图、Agent 清单与 I/O 契约、工具列表、全局上下文字段表、单 Agent System Prompt、截图证据），完成完整产品架构逆向分析。**本轮只产出一份独立交付物：产品全景架构图.html**（内含全部分析内容）。

## 一、证据与安全边界

- 只读查看，不触发任何生成/删除/购买/覆盖操作；不查看或输出凭证和敏感信息
- 外部补充资料只用官方站点、官方文档或页面公开信息；不使用第三方猜测作为证据
- 无法从前端确认的后端语言、数据库、消息队列、云服务，不得写成已确认事实
- 所有结论标记：【已确认】【合理推断】【建议设计】【未知】

## 二、事实来源清单

用户操作、聊天记录、Agent 名称、页面按钮/表单、画布资产、历史版本、模型选择、工具结果、错误提示、计费信息、官方资料。

## 三、还原核心功能域

从用户视角识别功能域，按产品实际检查（以下为通用清单，不要求全覆盖）：账号与权限、首页/项目入口、项目管理、需求输入与管理、风格/参数选择、核心资产设计（角色/场景/内容等按产品类型）、生成能力（图/文/音视频）、预览与编辑/剪辑、历史版本、资产库、分享与发布、积分/额度/计费、错误反馈与任务状态。

## 四、端到端功能流转（五条流）

选一个完整任务从进入到产出，同时表现：1. 用户交互流 2. Agent 控制流 3. 工具调用流 4. 数据与全局上下文流 5. 资产流。每步写清：谁触发、谁处理、读取什么、做什么判断、调用什么工具、生成什么结果、写回什么状态、是否需要用户确认、交给谁、失败分支。

## 五、产品分层架构（9 层，不预设每层已被确认）

1. 用户与渠道层（账号、登录权限、会员、余额、偏好、用户资产库、历史项目、分享渠道）
2. 交互与工作台层（聊天界面、Agent 身份展示、画布、资产卡、表单、确认按钮、任务面板、预览器、编辑器、历史记录、错误提示）
3. 产品应用层（项目/需求/资产/版本/发布等各管理模块）
4. Agent 与流程编排层（主控 Agent、专业 Agent、触发条件、工作流、状态机、用户确认门、任务移交、中断、回退、重试、幂等、完成条件）
5. 工具与服务层（上下文读写、解析提取、提示词生成、各类生成服务、合成、预览导出、安全检查、余额检查、计费、资产存储）
6. 模型接入与路由层（各模态模型、适用场景、限制、成本、延迟、失败率、切换重试。页面只出现一个模型时不得推断具备完整动态路由）
7. 全局上下文与数据层
8. 知识与公共资产层（风格库、模板、领域知识、提示词模板、规则、公共与私有资产隔离）
9. 基础设施与治理层（认证、权限、存储、CDN、数据库、任务队列、模型网关、日志、链路追踪、评测、安全、成本控制——只能写需要的能力/可能选型/推荐方案/不能确认的原因）

## 六、全局上下文架构

不要画成无结构的大框，按领域拆分（参考模板，可按产品调整）：UserContext、ProjectConfig、核心内容 Context、AssetContext、WorkflowState、BillingContext、EvaluationContext。只有页面有证据时标为真实字段，否则标"合理推断"或"建议设计"。

## 七、知识架构

区分"项目数据"与"可复用知识"，回答：知识如何变成模型可执行信息、资产如何跨步骤复用、系统如何知道模型能力边界、安全/计费规则在 Prompt 里还是由工具强制执行、用户反馈是否沉淀为知识、私有与公共资产如何隔离。

## 八、关键产出

1. **数据实体表 + Mermaid ER 图**：识别核心实体及关系（参考：User、Project、Conversation、Agent、AgentRun、Workflow、Task、ToolCall、Asset、AssetVersion、UserConfirmation、ModelInvocation、Error、BillingRecord、Feedback——模板不代表真实表名），注明哪些关系有页面证据、哪些是推导
2. **端到端时序图**（Mermaid sequenceDiagram）：以一个完整任务为例，参与者含用户、工作台、主控/专业 Agent、状态服务、全局上下文、工具服务、模型网关、资产服务、安全与计费；表现输入、确认、上下文写入、异步等待、资产写回、修改、失败、中断、交接
3. **产品全景架构主图**：从上到下完整分层；同层组件同一 subgraph；箭头标注调用/读取/写入/事件/确认/资产引用/状态更新；**实线=已确认、虚线=合理推断、点线或特殊颜色=建议设计**；必须有图例；画出关键数据和状态流转；标记产品当前没做好的校验机制和问题
4. 主图自检：一个普通产品经理能否从图中回答——需求从哪进入、谁决定调哪个 Agent、每个 Agent 输入从哪来、调用什么工具、产物由谁生成、结果存哪、下游如何拿到上一步资产、用户如何确认修改、失败后怎么办、余额不足在哪拦截、知识从哪来、如何保证资产一致性、为什么会出现状态不一致、系统如何知道任务真正完成

## 九、As-Is / To-Be 与风险

- **当前架构 As-Is 表**与**建议架构 To-Be 表**：重点检查是否需补充统一状态事实源、结果质量校验、一致性校验、资产依赖失效机制、重试幂等、额度预估与冻结、Agent 完成门、全链路追踪、效果反馈、局部重算
- **架构风险清单**（按优先级）：状态冲突、口头完成但工具未完成、资产生成成功但上下文未更新、上游修改后下游未失效、自动重试重复扣费、校验缺失、安全误判、中断后后台仍执行、私有资产泄漏、公共知识过期、模型能力变化后路由未更新
- **架构组件—证据追溯表**：组件 / 为什么需要 / 证据 / 已确认或推断或建议 / 置信度。没有证据也没有清晰设计理由的组件不进主图
